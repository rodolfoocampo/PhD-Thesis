
\chapter{Beyond Chat: Collaborative Editors Enhance Human Involvement and Agency When Co-Writing with Large Language Models} \label{c:tc5} 


\section{Link to Thesis}
This chapter begins to traverse the interaction design space of dialogic co-creativity, addressing RQ2: \textbf{how do the elements of dialogic co-creativity influence user roles and agency}? Specifically, it examines two principles from the framework: bidirectional communication and shared collaborative space, as well as the distinction between interaction \textit{about} the creation and interaction \textit{through} the creation. Through this chapter, I ask: how does the co-creative interaction in writing change when humans and AI interact only through a chat interface, versus when they also have access to a shared workspace? To investigate this, I developed two prototypes: one providing only a chat interface, and another providing both a chat interface and a shared text editor where human and AI can collaboratively write and edit.
\subsection{Background and Research Context}
Since my initial 2022 exploration of dialogic interaction (Chapter 3), the field has converged toward conversational interfaces as the dominant paradigm for interacting with Large Language Models (LLMs). While these interfaces facilitate interaction about'' the creative product, I argue they lack the necessary space for interaction through'' it. This chapter tests the hypothesis that a hybrid interface---integrating a conversational chat window with a stateful collaborative text editor---can better support these two interaction modes and mitigate the risk of user alienation from the creative process.
The work presented here describes the iterative development and testing of two functional prototypes: \textbf{Vorges} and \textbf{Common AI}. These systems allow the user and the AI to simultaneously converse and edit a shared piece of writing in separate but integrated spaces.
\subsection{Summary of Findings}
The evaluation of these prototypes through two user studies provides empirical evidence for the following insights:
\begin{itemize}
\item \textbf{Role Distribution}: Chat-only interfaces predominantly position users in directive roles (providing instructions and requests) while the AI assumes the role of primary executor. In contrast, hybrid interfaces encourage a more balanced partnership, with users participating more actively in the ``action space'' of writing.
\item \textbf{Agency and Involvement}: Users reported higher levels of perceived agency and active involvement when using the collaborative editor compared to chat-only conditions.
\end{itemize}

\section{Clarifications on Interpretation of Results and Constraints}

In interpreting these results, several points of caution identified in early reviews are worth noting:
\begin{itemize}
\item \textbf{Causal Attribution of Non-Significance}: Where quantitative measures did not reach statistical significance (e.g., specific enjoyment metrics), I refrain from definitively attributing this to ``low sample size.'' Such results may equally indicate a true lack of effect or suggest that the benefits of hybrid interfaces are more qualitative and process-oriented than purely outcome-driven.
\item \textbf{Measurement of Creative Agency}: In Study 2, participants' descriptions of ``higher'' creative agency are treated as subjective perceptions relative to their general experiences with popular tools like ChatGPT, rather than a direct comparative measure between the two prototypes.
\item \textbf{Tool Constraints and Confounds}: Study 1 compared two conditions: a chat-only interface and a hybrid interface combining chat with a collaborative text editor. However, the first prototype (Vorges) operated under technical limitations worth considering. In particular, the AI in the collaborative editor lacked fine-grained editing capabilities: the AI collaborator could not perform targeted insertions, deletions, or word-level modifications, and instead had to replace the entire document text even for minor changes. This means that when a user asked the AI to, for example, fix a single sentence, the system would overwrite the full text in the editor with an updated version. This wholesale replacement mechanism, combined with the fact that there was no visual signalling of where the changes had been made, may have independently shaped participant perceptions in ways that are difficult to disentangle from the effect of the interface modality itself. That said, the direction of this confound is worth considering. One might expect that having the AI repeatedly overwrite the user's entire text would \textbackslash{}emph\{undermine\} a sense of agency and personal contribution in the editor condition, making the AI's presence feel more heavy-handed than a targeted edit would. The fact that participants in the editor condition nonetheless reported higher levels of involvement and were more likely to see themselves as active contributors despite this limitation suggests that the core finding holds: the presence of a shared collaborative space separate from the chat, even one with clunky editing behaviour, appears to have contributed to shifting the dynamic away from pure delegation toward more active participation. The improved protocol in Common AI (Study 2) indeed addressed the capability for fine-grained edits in the editor by the AI (though not their visibility), lending additional support to the findings. However, that study crucially lacked a comparative control condition. The above suggests high potential for further research examining interface affordances and technical implementation that facilitate greater user involvement, agency, and collaborative dynamics when working with AI co-writers.

\end{itemize}

\subsubsection{Technical Documentation: Vorges Implementation}

The Vorges prototype is implemented as a Node.js web application using the Fastify framework. The frontend uses Handlebars templating with a split-pane layout: a text editor on the left and a chat interface on the right. When a user sends a chat message, the frontend automatically captures the current editor state and embeds it in the request sent to GPT-4o via the OpenAI API. The model's response is parsed on the client side to extract both chat messages and editor modifications.

\paragraph{The Curly Bracket Protocol}

Vorges uses a simple text-based protocol to enable the model to decide between chat and editor responses. When the user sends a message, the current editor content is automatically appended to the request in curly brackets:

\begin{verbatim}
userMessage + " The current text in the editor is: {" + editorContent + "}"
\end{verbatim}

The system prompt instructs GPT-4o to use a specific format:
\begin{itemize}
    \item \textbf{Text in curly brackets} \texttt{\{text\}}: Content to be placed in the text editor
    \item \textbf{Text outside curly brackets}: Messages to display in the chat interface
\end{itemize}

When the model wants to modify the editor, it returns the complete text that should appear in the editor wrapped in curly brackets. The frontend parses the response using a regular expression to extract bracketed content, clears the editor, and types the new text into it using an animated typing effect. The bracketed text is then removed from the message before displaying it in the chat interface.

The model can respond in three ways:
\begin{enumerate}
    \item \textbf{Chat only} (interaction \textit{about}): Text without curly brackets appears only in the chat interface.
    \item \textbf{Editor only} (interaction \textit{through}): Text wrapped in curly brackets replaces the entire editor content.
    \item \textbf{Both}: The model can include both bracketed and unbracketed text to simultaneously update the editor and display a chat message.
\end{enumerate}

\paragraph{Limitations and Evolution to Common}

The curly bracket protocol has several limitations that led to the development of Common's approach:
\begin{itemize}
    \item \textbf{Full text replacement}: The model must return the complete editor text, not incremental changes, which is inefficient for large documents.
    \item \textbf{Single state capture}: Only one editor state is transmitted per message, so rapid consecutive edits may miss intermediate states.
    \item \textbf{No granular editing}: The protocol cannot specify precise edits but requires replacing the entire editor content.
\end{itemize}

\subsubsection{Technical Report: Chat-Editor Co-Creative Application}

The core innovation of the Common prototype lies in a more structured prototocol for chat and editor communication, using JSON to enable the model to perform more granular edits in the text editor.

The system prompt instructs GPT-4o to respond in a structured JSON format that allows it to choose how to interact:

\begin{verbatim}
{
  "playground": {
    "add_end": "Text to append",
    "add_beginning": "Text to prepend",
    "edit": { "original": "...", "new": "..." },
    "delete": "Text to remove"
  },
  "chat": {
    "message": "Chat message to display"
  }
}
\end{verbatim}

The model can respond in three ways:
\begin{enumerate}
    \item \textbf{Chat only} (interaction \textit{about}): When the model needs to ask questions, clarify intentions, or discuss the creative work, it populates only the \texttt{chat.message} field.
    \item \textbf{Editor only} (interaction \textit{through}): When the model should directly modify the text, it populates the \texttt{playground} fields (add, edit, or delete operations).
    \item \textbf{Both}: The model can simultaneously respond in chat and modify the editor, enabling it to explain its edits or discuss while making changes.
\end{enumerate}


\paragraph{Web Implementation Overview}

The Common prototype is implemented as a Node.js web application using the Fastify framework. The frontend uses Handlebars templating and JavaScript to manage the dual interface: a split-pane layout with a text editor on the left and a chat interface on the right. When a user interacts with either component, the frontend captures both the chat message and the current editor state, sending them together to a backend endpoint that forwards the complete context to GPT-4o via the OpenAI API. The model's structured JSON response is parsed by the frontend, which then updates both the chat display and applies any editor modifications automatically.
